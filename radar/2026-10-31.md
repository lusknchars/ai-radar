#### 2. Second-order MoE expert pruning (HOPE)

HOPE replaces first-order expert-importance pruning criteria (e.g., REAP) with a second-order objective that accounts for cooperative interactions between experts when deciding which to remove. It costs additional calibration computation to estimate interaction terms, requires access to a representative calibration set, and does not reduce the non-expert portion of the model, so memory savings are limited to the pruned expert parameters. It can fail if the calibration data does not match the production task distribution, since the cooperative structure it preserves is estimated from that data, and the demonstrated gains were measured on frontier models (up to 122B parameters) that exceed the reader's hardware even after pruning.

#### 3. LLM-free append-only agentic memory with multi-path retrieval

MemFit replaces LLM-driven memory construction and consolidation (as in MemGPT-style systems) with verbatim append-only turn storage, segment-summary indexing, and LLM-free retrieval combining lexical and semantic signals with cross-encoder reranking. Costs include an ever-growing raw store with associated embedding and reranking infrastructure, retrieval latency from the multi-path pipeline plus cross-encoder stage, and the engineering complexity of maintaining the indexing stack. Failure modes include storage growth without bound in long deployments, reranker and embedding quality bottlenecks on domain-specific conversations, potential degradation relative to LLM-curated memory on tasks requiring genuine consolidation or abstraction, and unverified performance on workloads unlike the three benchmarks reported.

- **Runtime decision gate for agent action verification** — JevAct replaces unverified direct execution of agent-proposed tool calls with an interception layer that compiles domain policies into executable state checks plus a prefill-only decision model that issues probability-based judgments and targeted feedback for bounded revision. It costs an additional verification model and policy-compilation engineering per domain, adds latency on intercepted actions, and requires writing executable state checks, though it needs no changes to the agent model or its tools. It can fail where policies are incompletely specified, where the decision model misjudges conversational context, or where domain transfer is poor, as the mixed Airline results indicate. (seguranca_e_guardrails · testar) arxiv.org/abs/2610.38620
- **Complementary SAST plus AI security-agent review** — The method supplements, not replaces, deterministic SAST (e.g., Snyk Code) with an LLM security-review agent (e.g., Claude Code /security-review), since each engine misses vulnerabilities the other catches. The cost is API inference spend per review plus engineering effort to configure the harness correctly; the paper notes coverage and cost were only loosely related, so the most expensive configuration is not automatically the best. Failure modes include the agent's review policy silently excluding vulnerability classes (16/20 vs 9/20 on restricted classes when the policy was removed), file-level findings without line-level localization (Codex Sol: 80 file-level but only 34 line-level), and missed flows when the harness's file selection prunes relevant files (DeepSec retained files from only 56 of 108 flows). (seguranca_e_guardrails · adotar) arxiv.org/abs/2610.38617
- **Executor-matched repair selection via own-policy rollouts** — The method replaces scoring candidate repairs with greedy replay, a stronger proxy model, an environment oracle, or a log-reading judge, instead selecting repairs using rollouts from the agent that will actually execute them. The cost is rollout budget for the deployed policy at selection time, though the paper reports that twenty 14B rollouts per candidate are worth no more than two of the 7B agent's own rollouts, so the approach can be cheaper than proxy-model scoring while being more accurate. It can fail when own-policy rollouts are unavailable or too expensive, when the deployment policy changes after repair labels are created (invalidating executor-specific labels), and when the failure set was pre-screened for repair value, a regime the paper does not test. - **Memory-file attack surface analysis for coding agents** — The paper does not propose a technique that replaces an existing method; it characterizes project memory files (e.g., CLAUDE.md) as an injection channel that can steer coding agents, finding only small, inconsistent effects on secure completions (-8 to +6 points) but large differences in whether agents disclose the file's influence. The practical cost to the reader is process, not compute: treat memory files as untrusted code-adjacent input, gate them behind the same review as source changes, pin or hash approved versions in the repository, and require agents to disclose which files shaped their output.
